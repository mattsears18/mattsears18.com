In June I wrote about [building shipyard](/blog/shipyard-and-lightwork), an
autonomous engineering loop on Claude Code. In July I wrote that
[everyone else had built the same one](/blog/everyone-built-the-same-loop),
and that a meaningful chunk of my plumbing had quietly become native.

I ended that post saying the trick is to keep asking the machine what it's
missing. So in September I asked again, and the answer was: _most of me._

## The easy part

Some of it really was dead weight, and the numbers were embarrassing.

**176 of 258 scripts were tests of shipyard itself** — 66,784 lines of
self-test against 36,333 lines of tool. 119 of those had no executable at all;
they asserted on prompt _markdown_, checking that two hand-copied versions of
the same instruction still matched.

There was a 519 KB design-rationale file living in the directory the
orchestrator reads specs from, one over-eager file read away from eating a
context window. There was a whole second dispatch system kept as a "reversible
alternate," which had been found non-functional months earlier and was still
being recommended as a fallback.

I deleted about 11,000 lines in four passes. All of it was redundant with
something else in the repo, or wasn't in the execution path at all.

Then I got to the part I was actually excited about.

## Uncle Bob got there first, sort of

On 4 August, Robert C. Martin
[described](https://x.com/unclebobmartin/status/2084638878548304046) building
an orchestration harness for "a squad of agents" driven by a state machine,
with a simulator and Monte Carlo testing over it. He signed off: _"Don't tell
me software engineering is dead."_

Five weeks later, [he wrote](https://x.com/unclebobmartin/status/2098432570887217520):

> And while I was heads-down getting that to work, the agents got a LOT
> better. So much so that when I came up for air, the need for my harness was
> obviated.

Anthropic's own team says the same thing with numbers: they
[cut ~80% of the Claude Code system prompt](https://simonwillison.net/2026/Jul/21/cat-and-thariq/),
and now ship _a different system prompt per model_, because only the frontier
ones can go without the training wheels.

So I made a table. Shipyard polls CI; the harness has a `Monitor` tool — tick.
Shipyard tracks session state; the harness has `TaskCreate` — tick. Sixty-two
ticks out of eighty scripts. 76% of the lines.

I was going to write a post about deleting three quarters of my own tool.

## Then I opened the files

`gh-cached.sh`, which I'd marked replaceable by the GitHub MCP, is a TTL cache
with explicit post-write invalidation. The MCP has no cache. Swapping them
doesn't remove a redundancy — it adds API calls.

`session-state.sh`, marked replaceable by `TaskCreate`, writes to
`.tmp.<pid>` and renames, so a process killed mid-update leaves the previous
state intact instead of a corrupted file. `TaskCreate` is a todo list.

And my favourite. `assert-ci-green.sh` exists because
`gh run list --commit <sha>` silently matches **zero runs** when you hand it an
abbreviated SHA — and exits 0. So the obvious three-line version of "is this
commit green" passes on the empty set. It reports green having looked at
nothing. The script's stated purpose is that it "can never answer green
without having observed at least one run."

Five rows fell over in an afternoon. So I stopped guessing and had all 82
headers read properly — contract, not category.

**Zero.** Not one script had a genuine first-party replacement. Seventy-three
had none at all. The remaining nine are obsolete only if I delete the spec
corpus, which documents the seventy-three that are staying.

## Why the illusion is so convincing

Every one of those scripts is, at the category level, exactly what I said it
was. A cache. A state store. A CI check. And the platform genuinely has a
cache-shaped thing, a state-shaped thing, a CI-shaped thing.

What it doesn't have is _the specific property each one was written to
guarantee_ — don't call this green unless you saw a run, don't let a killed
process leave a half-written file, don't ask GitHub the same question four
times in one session.

Every one of those exists because something went wrong once.

And none of them are visible from outside the file. You cannot tell a script
that polls CI from a script that polls CI _and refuses to lie about an empty
result_ by looking at its name, its size, or what category it belongs to. You
have to open it.

A category match tells you two things do the same kind of work. It tells you
nothing about whether one can replace the other. I wrote a confident table
that would have deleted about 8,800 lines on exactly that confusion.

## What I'd say now

Uncle Bob is right, and I don't want to soften it: a harness built to
_constrain_ a model gets obviated when the model stops needing constraining. I
removed the parts of mine that did that, and I'd remove them again.

But that's not what most of my harness turned out to be.

The rest of it is memory. Seventy-three scripts, each one a thing that went
wrong once, compressed into a check that won't let it go wrong again. A
smarter model doesn't make any of them less true. It just makes them easier to
mistake for scaffolding.

My July post said the plumbing converged and the judgment didn't. I'd put it
more sharply now. The plumbing that converges is the plumbing that never had
to be _right_ about anything in particular. The moment a script encodes a
reason, it has stopped being plumbing — it's a decision someone made after
being burned, wearing plumbing's clothes.

I went looking for scaffolding to tear down and found a scar.
